# plan-review 报告的解读参考（结论区）

> **规则**（在各 agent 的 system prompt / AGENTS.md 里）：
> plan-review 是**候选清单生成器**，不是交付闸门；缺陷抓得住，但存在**优先级膨胀**
> —— 倾向把「加固建议」升格为 P0/P1 ⇒ **逐条复核后再采纳**。
>
> 本文件只放**实测结论**（按需读，不自动注入上下文）。

## 实测基线

- 来源：项目 `docs/plan/20261016-plan-review-benchmark.md`
- 缺陷**召回 5/6**，人工复核 **6/6**
- **优先级膨胀**：倾向把「加固建议」升格为 P0/P1
- 逐条复核后**事实性误报 0 条**

## 解读要点

1. **不把 plan-review 当闸门**：它的产出是候选清单，需要主 agent 逐条复核后自行取舍。
2. **提防优先级膨胀**：加固类建议常被写成 P0/P1 ⇒ 复核时按「是否阻断交付」重新定级。
3. **事实性误报率低不代表可以直接采纳**：仍需核对它引用的文件/行号是否真实存在、是否已过时。

## 补充实测：design-review 改造后首轮（n=1，样本 = design-review 下一步方案 v1）

- 结构遵从 **3/4**：稳定 ID ✅、真实缺陷/加固建议性质判定 ✅、结论档合门禁 ✅、**E1-E4 证据等级标注 ❌**
- 引用行号抽检 3/3 属实（`opencode.jsonc:370`、`:425-428`、`:450-452`）⇒ 误报率仍低
- 判 P1 两条，逐条复核成立（契约冲突致观测失真 / 复审覆写丢档）⇒ 本轮**未观察到膨胀**，但 n=1 不足以推翻既有基线
- 缺项归因假设：plan-review 的 agent system 未要求证据等级/追溯表 ⇒ 双契约并存时 skill 新增块「部分生效」，待三方对照验证

## A1 校准记录（第 2 次提样：r2 / 复审场景，样本 = 20261027-design-skill-consistency）

记录 6 项（口径见 `docs/plan/20261027-design-review-next.md` A1）：

2. **有性质判定** ✅ — 真实缺陷 5 条、加固建议 3 条、❓ 1 条，逐条带分级依据
3. **有证据等级** ✅ — 逐条标 E1/E2（外部事实标 ❓）；**与首轮（缺该标注）的唯一差异是调用 prompt 显式点名要求** ⇒ 归因：plan-review system 未要求，skill 要求需被 prompt 强化才落实
4. **结论合门禁** ✅ — 无 P0、P1×1 ⇒ 「有条件通过（待确认 2 项）」，与 `SKILL.md` 门禁第 3/5 条一致

6. **复核后降级** — r2 的 P1 仅 1 条，复核 **0 条成立**（1 条误报）；真实保留 2 条（断言与先例互斥、证据表无落点）；3 条已消解、1 条降 P3

**误报根因（重要）**：不是优先级膨胀，而是**取证时点与并发写入冲突** —— 被审 4 个文件在 18:36-18:38 被并发改动，r2 读到「哲学层未落、仅生成器节已落」的中间态，据此判「悬空引用」。已回灌 `SKILL.md` 步骤1「证据时点」条款。
**结论**：步骤6 复审闭环可用（21 条核销三态齐全、ID 沿用无漂移）；证据等级是否需要写进 plan-review 的 system，待第 3 次提样（不显式要求时）再判。

## W8 结构自检的实测（4 次派发，2026-10-27 20:2x-20:3x）

| # | 输出 | 判定 |
|---|---|---|
| 1 | 仅剩标点片段（伪工具调用残留） | 不可用 |
| 2 | 内容有效但被输出上限截断 | 块不可核 |
| 3 | 10 块齐全 + 「结构自检回执」自报 `0/5/4/3` 与正文标记 12 条一致 | ✅ 首个自证样本（`sample-07`） |
| 4 | 写到追溯表即止，末句为「（详细清单见下文续块）」 | 截断 |

- 结论：**W8 对「缺块」有效**（首个「块齐 + 计数自证」样例），不必再加码措辞。
- 新发现：4 次里 2 次**根本不是缺块，而是篇幅超过输出上限被截断**（甚至自造「续块」指针）⇒ 已记 **W9 提案（未实施）**：篇幅预算（≤120 行 / ≤12 条，超限先砍 P3 与低影响 P2，**截断条目、不截断块**，禁止「见下文续块」）。按纪律 W9 须先过 plan-review 再落。
- 教训：**结构自检管不到「交不出来」**。实验设计里「输出长度」是独立变量，验证模板类改动时须同时记录「是否完整交付」，否则会把截断误记为「规则无效」。
