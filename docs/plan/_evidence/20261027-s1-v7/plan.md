# 实现计划审核清单（计划可执行性）

> 被 `SKILL.md` 步骤3引用：审核对象为**实施前**的实现计划、任务拆解、落地步骤（如 `docs/plan/*.md`）时读取本文件。
>
> **边界**：审"计划能不能被另一个人/另一个会话直接执行且不产生歧义"，不审代码正确性（真实 diff 交 `review`）；架构取舍交 `architecture.md`；接口契约交 `api.md`。

## 核心判据

一句话：**计划是"执行者无法独自决定的事"的集合**。凡是执行者必须回头问作者才能动手的地方，都是缺陷。

## 检查项

- **目标与不做**：目标能否一句话验收；是否写明**不做什么**（防范围蔓延）；与需求文档是否对齐
- **落点精度**：每个改动是否有精确文件路径 + 类/方法/字段级落点；新建文件的完整路径。"某处/相关模块/适当位置/统一处理"⇒ ❌
- **现状依据**：方案引用的既有类/方法/签名/配置项是否真实存在（E2 核实）；有无凭空假设的 API、字段、开关
- **顺序与依赖**：步骤顺序是否真的可执行（前置产物先生成）；并行/串行是否标注；有无循环依赖或"先改 A 才能改 A"
- **单步可观察性**：每一步做完是否有可观察结果（编译过 / 测试过 / 命令有预期输出）；无则标 ⚠️
- **验收方式**：是否给出具体命令 + 预期输出（不是"跑一下测试"）；无法自动验证的部分是否说明人工判定标准
- **占位符与空洞**：TBD/待定/后续补充/类似处理/"补充必要校验"/"处理边界情况" ⇒ ❌ 不可实施；需替换为具体动作
- **名称与契约唯一性**：跨文件共享的类名/方法名/字段名/配置键是否唯一确定，避免各执行者自造同名不同意
- **边界与失败**：异常、并发、生命周期、数据/配置迁移、幂等是否列出；失败后发生什么是否写清
- **回滚与灰度**：涉及数据、配置、发布、权限时是否有回滚路径与最小灰度单位
- **验证闭环**：是否说明"改完怎么证明对了"（静态检查、相关测试、真机/手工项分列）
- **范围纪律**：有无"顺手重构"混入无关改动；无法量化收益的重构是否单独立项

## 移动端专项（涉及原生层时）

**触发判断**：计划含以下关键词时自动读取 `mobile-delta.md` 对应节：
- 架构层：推送、通信边界、热更新、后台、环境映射、崩溃、深度链接、深链
- 代码层：权限、签名、分包、最低版本、生物识别、Keychain、Keystore、内更、强更

读取 `mobile-delta.md` 的「代码层差异」+「原生稳定性差异」节，其余共性项沿用本清单。额外确认：双端改动是否成对列出（仅写一端 ⇒ ❌ 缺项）。

## 输出要求

遵循 `SKILL.md` 步骤4 与「输出纪律」：✅ 项合并一行，仅 ⚠️/❌/❓ 展开，每条格式：

`[P?·真实缺陷|加固建议] 位置 - 问题 - 证据<E?> - 建议动作 - 影响/触发条件`

计划类方案必须输出「追溯表」（需求/目标 → 方案落点 → 验收方式 → 状态），空白落点即为 P0/P1 候选。
复审核销表按 `| 条目 ID | 状态 |` 两列输出（状态限于 已修复/部分修复/未处理），与 `SKILL.md` 步骤6 一致，便于脚本计数。
