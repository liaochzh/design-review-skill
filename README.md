# design-review

一个用于 **方案审核** 的 agent skill：在动手之前审「实现计划 / 架构方案 / API 设计」，回答的不是「写得像不像方案」，而是**能不能直接落地、有没有漏、需求是否可测**。

> 面向 opencode / Claude 一类支持 `SKILL.md` 的 agent 运行时。纯提示词实现，无脚本、无依赖。

## 它解决什么问题

| 常见失败 | 本 skill 的做法 |
|---|---|
| 评审报告写成读后感，读完不知道要改哪 | 逐条清单强制七字段：ID / 判定 / 位置证据 / 触发条件 / 影响 / 建议动作 / 分级与依据 |
| 「文档没写」被直接判死，其实仓库别处早已定 | 证据分四级 E1–E4：**E2 要求先查别处**，未定才标 ❓ Gap |
| 建议全是「考虑性能 / 注意安全」 | 不可执行的建议一律不报；同一根因的多个症状合并为一条 |
| 报告越长越显得认真，最后被输出上限截断 | 交付前两查：**结构自检**（块齐 + 计数自证）+ **篇幅预算**（≤120 行 / ≤12 条，截断条目不截断块） |
| 复审时条目对不上，不知道上轮修没修 | 复审必带「上轮问题核销表」（两列三态），跨轮靠**内容锚**（位置 + 问题语义），不靠 ID |
| 同一方案重跑两次结论不一致还以为是 bug | 已验证：**结论档大体稳定（7 次里 6 次同档）但会因 P0 判定分歧跳档**；条目集合与条目级分级不稳定 ⇒ 重跑只用于交叉取证 |

## 何时触发

方案 / 设计文档 / 实现计划 / 任务拆解 / API 设计**实施前**评审。触发词：审核方案、评估设计、检查可行性、找遗漏、方案评审。

**不适用于**：已完成的代码 diff 审查（用 review 子代理）、编译/运行报错（用 `code-error-fixer`）、真机复现取证（用 `debug-loop` / autoDebug）、产品咨询与 PRD（用 `product`）。skill 的 `description` 已写明这些排除关系。

## 输出纪律（三组 8 条）

- **① 说什么**：✅ 通过项合并一行；只展开 ⚠️/❌/❓；不报清单（纯风格偏好、不可执行建议、重述合理取舍）
- **② 怎么说**：每条非通过项标证据等级 E1–E4；评分锚定 5→1 与 P3→P0 对齐；两档「精简」不混用
- **③ 交什么**：结构自检（块齐 + 四数自证）+ 篇幅预算（P0/P1 不设限，超限转长报告模式）

## 已知边界

- **截断是概率性的**，不是确定性长度上限：206 行曾有完整交付，>150 行也有两次被截断 ⇒ 篇幅预算只压低风险，不承诺「必然成功」。
- 真实使用时报告由**派发方转录**落盘，`执行模型 / 结构自检回执 / E1–E4` 三字段可能整体缺失 ⇒ 一律记「不可归因」，不得当作 skill 失败（详见 `references/plan-review-reading.md`）。
- 观测样本覆盖两个模型（qwen3.8-flash / GLM-5.3-Flash），**未做模型级结论**（n=1）。
